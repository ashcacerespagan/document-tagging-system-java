I can’t blame you for having this idea initially, though, as even the Oracle
Java SE docs have the potential to lead you astray:
One of the primary purposes of inheritance is code reuse: When you want to create
a new class and there is already a class that includes some of the code that you
want, you can derive your new class from the existing class. In doing this, you can
reuse the fields and methods of the existing class without having to write (and
debug) them yourself.
I will state this outright: inheritance is an extremely poor way to just reuse
code. Its entire design semantics center around the concept of an is-a
relationship between the superclass and subclass, a key aspect of its design
which plain code reuse completely ignores and destroys. This is where MVC
frameworks and other libraries have enforced bad practice by utilizing
convenience classes designed to be extended by client applications simply
for code reuse, making it very easy to assume that this “feature” of their
framework correlates to good ways to engineer code. What eventually
happens when the programmer embraces this idea is instead a maintenance
nightmare reminiscent of the spaghetti monster, where classes are coupled
together for no good reason and one change breaks a million unit tests.

combine the two in harmony. You’ll find that a lot of design patterns work
this way and that there was never any need to vilify inheritance or deify
composition or anything else of the sort.
Second, the key to this whole design pattern is that our decorator classes
implement the same interface that our composed, concrete list
implementation does. This enables us to both compose the core
functionality of the list implementation while extending the functionality of
the classes that decorate it. Only a couple of design patterns work this way,
but this is the only one I’m aware of that allows us to recursively compose an
unlimited number of objects with complimentary, but differing,
functionality.
Third, even though we use inheritance to extend the decorators, because
we’re able to add functionality at runtime through what I like to call
“dynamic composition,” our functionality isn’t statically coupled together.
This is one of the biggest shortfalls of using strictly inheritance to
implement this type of solution. This is mentioned in the article above as
well, and it’s clearly illustrated here. If we added a few more classes of
decorators and then iterated through all the runtime combinations of
dynamically composed objects, coding the equivalent in static inheritance
hierarchies would result in an obscene number of classes, and it would be
rigid, inflexible, and a maintenance nightmare.

Long time Java programmers might wonder where the default case and

that all of the cases are covered in the switch, removing the need for a
default case. Additionally, now that switches support pattern matching, they
take care of all the instanceof checking and type casting under the hood.
Looks kind of like a functional language now, huh? What it also looks like is
that we’re able to process different implementations in different ways

superclass like we would typically try to do with an inheritance-based
solution. That doesn’t mean that inheritance can’t help us create something
more elegant and flexible, however. This pattern matching solution could
easily snowball into a maintenance bottleneck and make it harder to add or

Would you believe that those two lines achieve everything that the switch
statement did? Obviously our solution required a few steps, but consuming
our classes and dispatching the correct type-safe business logic is as simple
as that. In the process, we gained the extensibility we need to add or amend
functionality without breaking our entire workflow or ending up with a fifty-
line-long case statement. PaymentMethod#process is what we call our visitor
method, and PaymentProcessor is our visitor. You may be thinking that the
process implementations with the single paymentProcessor.process(this) are
the most boring parts of this whole pattern, and you’d be right. However,
they’re also the most important parts because they determine exactly which
instances of both the visitor method and the visitor class’s methods get
dispatched at runtime. It essentially replaces the branching logic of the
switch with built-in polymorphic method dispatch that branches our logic

FP fans like to tout their favorite language’s more declarative programming
style over the typically more imperative approach of languages like Java, and
I can appreciate that. However, of these two examples, doesn’t the glorified
if-else of pattern matching cases look a lot more imperative than the visitor
method calls? You decide for yourself. Now this doesn’t mean that I never

brothers, really.
